# recipe-sqlite-sqlc — SQLite + sqlc

## Problem

Talk to SQLite from Go with **type safety**: catch SQL mistakes at generation
time, not at runtime, and drop the boilerplate `rows.Scan(&a, &b, &c)` plumbing.

## Solution

**Two pieces:**

1. **sqlc** — a code generator. You write plain SQL with named queries
   ([`query.sql`](query.sql)) and run `sqlc generate`; it emits Go structs
   (`models.go`) and type-safe query methods (`query.sql.go`). A `:one` query
   becomes `func (q *Queries) GetFoo(ctx, id) (Foo, error)`; a `:many` query
   becomes `func (q *Queries) ListFoos(ctx) ([]Foo, error)`.

2. **`modernc.org/sqlite`** — a **pure-Go** SQLite driver (no cgo). The binary
   cross-compiles natively with `CGO_ENABLED=0`.

```go
import (
    "database/sql"
    _ "modernc.org/sqlite"            // registers the "sqlite" driver
)

db, err := sql.Open("sqlite", "file:app.db")
if err != nil {
    return fmt.Errorf("open sqlite: %w", err)
}
q := New(db)                           // *Queries, generated by sqlc
foo, err := q.GetFoo(ctx, 1)            // type-safe, no manual Scan
if err != nil {
    return fmt.Errorf("get foo: %w", err)
}
_ = foo
```

`store.go` ships a runnable, tested stand-in for the generated `*Queries` so
the recipe works without a live `sqlc generate`. Its shape is exactly what
sqlc produces (the `DBTX` interface + `New(db DBTX)` + typed methods), so it
teaches the real pattern — including the trick that the same generated code
works against both `*sql.DB` and `*sql.Tx`.

## The driver decision (cgo vs pure-Go)

| Driver | Verdict |
|---|---|
| `modernc.org/sqlite` | **Chosen.** Pure Go → cross-compiles, no C toolchain at build time. Fast enough for nearly all service workloads. |
| `mattn/go-sqlite3` | Requires `CGO_ENABLED=1` + a C compiler, and a full cross-toolchain for cross-builds. Rejected for a universal kit where build portability matters more than raw throughput. |

## Why sqlc over the alternatives

| Approach | Verdict |
| --- | --- |
| `database/sql` raw | Manual `Scan()`, no compile-time SQL checking — exactly what sqlc removes. |
| `jmoiron/sqlx` | Reflection-based scanning; still dynamic, no SQL validation. |
| `Masterminds/squirrel` | A query builder — not type-safe from SQL, and you stop writing SQL. |

sqlc keeps SQL as the source of truth and makes the Go a compile-checked mirror
of it.

## Workflow

```sh
# 1. Write schema.sql + query.sql (in this directory).
# 2. Configure sqlc.yaml (engine: sqlite).
# 3. Generate:
sqlc generate
# 4. Use the generated *Queries (mirrored by store.go here for testing).
```

## Verify the behavior (observable)

Run a small command that opens `Open("")`, calls `New(db).CreateFoo(ctx, "coffee")`,
then calls `GetFoo` with the returned id. Observe a printed row whose name is
`coffee` and whose id is non-zero. Close the database with `_ = db.Close()`.
This is the user-visible persistence check; passing unit tests is not a substitute.

## Run the tests

```sh
go test ./recipes/recipe-sqlite-sqlc/...
```

The test suite checks the data access mechanics in memory. It does not replace
running the observable persistence scenario with the built application.
