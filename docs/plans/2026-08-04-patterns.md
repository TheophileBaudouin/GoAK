# Plan — Patterns KitV2 (2026-08-04)

## Goal

Remplir `KitV2/knowledge/patterns/` avec 38 patterns positifs de qualité
professionnelle : problème/contexte/solution/forces, sources primaires,
liés aux rules/recipes et à l'anti-pattern homologue. Rapport :
`docs/research/2026-08-04-patterns-research.md`.

## Séparation patterns / anti-patterns (non négociable)

- Dossier distinct : `knowledge/patterns/` (les anti-patterns restent dans
  `knowledge/anti-patterns/`).
- Namespace d'ids distinct : `pattern:<domaine>:<slug>` (go, database, http,
  architecture, testing, security, observability, cli, messaging, config,
  cache, concurrency, resilience) — jamais `pattern:antipattern:*`.
- Schéma distinct (positif) : problem/context/solution/benefits/costs —
  pas de symptom/detect/fix.
- Lien explicite vers l'anti-pattern homologue via `relationships.references`
  (id de graphe résolu par le validateur) + `related` en prose pour
  rules/recipes.

## Format (contrat de graphe + champs positifs)

```yaml
id: pattern:<domaine>:<slug>      # GRAPH_ID_RE : pattern:<domaine>:<slug>
title: <Nom — verbe d'action>
kind: Pattern
version: 1
status: active
owner: go-agent-kit
tags: [go, <domaine>]
go_version: "1.22+"
dependencies: []
last_verified: 2026-08-04
problem: >-        # problème résolu
context: >-        # quand appliquer / signaux
solution: >-       # forme de la solution (API, shape, outil du kit)
benefits: >-       # pourquoi ça marche
costs: >-          # trade-offs / limites (rend le pattern utilisable)
related: >-        # rules/core/*, recipe-*, anti-pattern homologue (backticks)
relationships:
  references: [<URLs primaires>, pattern:antipattern:<slug-homologue>]
  uses: []
  validated_by: []
```

Contraintes validateur : kind Pattern, status active, id `pattern:<domaine>:
<slug>`, `references` = URLs OU ids de graphe existants (l'id anti-pattern
homologue doit exister — il existe, 47 livrés), prose ≤ 80 caractères (hors
URLs), pas de chemin metaprojet.

## Risques

- **Qualité vs volume** : 38 fichiers ; chaque fichier reste concentré
  (solution + forces). Tout fichier qui ne passe pas la revue est retiré
  ou fusionné.
- **Duplication avec rules/recipes** : le corps des patterns décrit la FORME
  (problem/context/solution/forces), jamais le code exécutable des recipes ni
  les règles opérationnelles ; `related` pointe au lieu de copier.
