# Research Brief: Deterministic Project-Structure Documentation for Go Projects and Agent-Kit Conventions

## Context

Governance decision: should a per-project `structure.md` (a reading map for non-developers — one-line role per top-level dir, typical reading path, internal vs public boundary, where tests live) be **deterministically generated** or **hand-maintained with validation-only freshness checks**? This brief evaluates the evidence across four angles.

---

## Angle 1: Deterministic Structure/Doc Generation in Go

### What exists

- **`go list ./...`** — The standard Go tool enumerates all packages in a module. With `-f '{{.ImportPath}}: {{.Dir}}'` it emits a machine-parseable list of every package directory [1]. This is the foundation for any tree-walking generator: it is deterministic, versioned with the Go toolchain, and requires no third-party dependency.
- **`gomarkdoc`** (github.com/princjef/gomarkdoc) — Generates markdown documentation for Go packages. Supports `--output '{{.Dir}}/README.md' ./...` to emit per-package docs, and a `--check` flag for CI drift detection [2]. However, it documents *API symbols*, not directory roles. It would need a custom template to produce a one-line directory-role summary.
- **`pkgsite`** (golang.org/x/pkgsite) — Google's official pkg.go.dev server; extracts and generates documentation for Go projects. It is a web server, not a tree-walker for directory maps [3].
- **`golds`** (go101.org/golds) — A Go local docs server and code reader that extracts maximal information from Go code. Again focused on API docs, not directory-role maps [4].
- **`dirtree`** (github.com/ThembinkosiThemba/dirtree) — A Go code analyzer that examines a repository and generates a hierarchical structural analysis in markdown, including package/function/method relationships [5]. Closest existing tool to a directory-role generator, but it produces detailed dependency graphs, not a one-line-per-dir reading map.
- **`clarion`** (github.com/dshills/clarion) — Scans a repo, builds a Fact Model, and uses an LLM to produce documentation. Not deterministic in the governance sense (LLM output varies), and overkill for a directory map [6].
- **`projectscan`** (Opendray) — Auto-detects a project's tech stack and key structure via shallow directory walk, emitting a markdown summary. Demonstrates the feasibility of deterministic tree-walking for structure docs, though it targets tech-stack detection rather than per-directory role descriptions [7].

### The "one-line role per directory" obstacle

**This is a real but solvable obstacle.** Go directories do not carry human-readable role metadata. A `tree`-based generator can list directories and their Go package names, but the *role* (e.g., "HTTP handlers", "internal auth logic", "CLI entry point") is semantic content that a static analyzer cannot derive from directory names alone. The `cmd/` and `internal/` conventions are well-known enough that a generator could infer roles for standard directories, but custom directories require either:

1. A convention (e.g., `cmd/*` = CLI entry point, `internal/*` = private implementation) — solvable for the common cases.
2. A human-authored annotation (e.g., a `// role:` comment in a `structure.md` source file, or a `.structure.yml` config) — this is the exception path.

**Verdict**: A generator can produce a *draft* structure.md with high confidence for standard Go layouts (cmd/, internal/, pkg/, api/, web/). The semantic reading-path explanations and non-standard directory roles require human input — making generation-first with manual semantic enrichment the correct pattern.

## Angle 2: Freshness/Anti-Drift Techniques for Generated Documentation

### Concrete, citable practices

1. **`git diff --exit-code` in CI** — The memstead project (Rust) uses a GitHub Actions workflow that regenerates API docs via `cargo run -p xtask -- generate-docs` and then runs `git diff --exit-code` on the output directory. If the regenerated bytes differ from what's committed, the workflow fails with `::error::` and instructs the contributor to regenerate and commit [8]. The xtask output is byte-stable on identical source, so a non-empty diff is always a real drift.

2. **`doc-drift` composite action** — A GitHub Actions composite action (chrysa) that runs `make <target>` (default `docs-code`) to regenerate code-derived docs, then fails on `git diff --exit-code -- <paths>` (default `docs/`). It emits a `::error::` with the fix command and a `--stat` of the drift [9]. This is a reusable, configurable pattern that any Go project can adopt by wiring `make structure-doc` as the target.

3. **Go's `// Code generated ... DO NOT EDIT` convention** — The Go toolchain mandates that generated files include a line matching `^// Code generated .* DO NOT EDIT\.$` before the first non-comment, non-blank text [10]. This marker serves double duty: it tells humans not to hand-edit the file, and it gives tools (linter, CI) a reliable signal to identify generated files. The `golangci-lint` linter has an option to strictly enforce this convention [11].

### Supporting pattern: `go generate`

Go's `go generate` command scans for `//go:generate` directives in source files and runs the specified commands. This is the standard mechanism for driving doc generation as part of the build pipeline. A `//go:generate` directive in the repo root can invoke a structure-doc generator, making regeneration a single command [12].

## Angle 3: Conventions from Agent Kits / Agent-First Repos

### What recognized sources say about structure documentation

1. **AGENTS.md (agents.md)** — The open spec (stewarded by the Agentic AI Foundation / Linux Foundation) defines AGENTS.md as a "README for agents." It is a single Markdown file at the repo root with sections for project overview, setup, commands, conventions, and boundaries. The spec has no required sections, but the dominant pattern across 60k+ repositories is a compact project map [13]. The spec explicitly says: "AGENTS.md is living documentation" and should be updated when commands, paths, boundaries, or patterns change [14].

2. **Agent-friendly repo conventions (taim.io)** — This guide recommends that a root AGENTS.md include a "project map" describing each major directory in **one sentence**, and that a "structure answer common questions" section make the common path easy to infer without pretending one layout fits every framework. It explicitly advises: "The best agent-friendly repo setup is not the one with the longest instruction file. It is the one that helps an unfamiliar contributor choose the right location" [15]. This directly supports a per-directory one-line role map.

3. **Agent Skills spec (agentskills.io)** — The specification defines skills as directories containing a `SKILL.md` with YAML frontmatter and Markdown body. The spec recommends progressive disclosure and keeping SKILL.md under 500 lines. Skills are self-contained and loaded on demand. The spec does not prescribe a project-structure reading map, but its emphasis on structured, machine-readable frontmatter with human-readable body is a relevant pattern [16].

4. **addyosmani/agent-skills** — The canonical agent-skills repository uses `SKILL.md` files with a recommended section pattern (Overview, When to Use, Core Process, Red Flags, Verification). The AGENTS.md for the repo itself is minimal and points to the skills directory. The repo does not include a project-structure reading map; it relies on the directory structure itself (skills/ subdirectories) as the navigation mechanism [17].

5. **Anthropic CLAUDE.md** — Claude Code reads `CLAUDE.md` files at project root and in subdirectories. The convention is plain Markdown with no required format. The guidance emphasizes that CLAUDE.md is "the briefing you would give a capable new teammate on their first morning" — including how the team does things, what to avoid, and where the important pieces live [18]. This aligns with a structure.md that serves as a reading map.

### What these sources say about generated vs. hand-maintained

The agent-kit ecosystem does not have a strong opinion on generation vs. manual maintenance for structure docs. The dominant pattern is **hand-maintained AGENTS.md/CLAUDE.md** with the understanding that it drifts and must be kept current. The taim.io guide explicitly frames the problem as: "One wrong choice may come from a difficult task; the same wrong choice twice exposes durable ambiguity" — implying that structure docs are validated by repeated use, not by automated regeneration [15].

However, the **generated-docs-as-drift-defense** pattern from the software-engineering community explicitly states: "A `--help` output that's accurate and a doc page that's three releases behind — that combination is worse than no doc page, because the reader trusts the doc page over the binary. Generated pages can't lie" [19]. This is the strongest articulation of the deterministic-generation argument.

## Angle 4: Does "Generated Cannot Lie" Hold?

### The claim: deterministic generation as governance default

The evidence supports a **qualified version** of this claim:

**Supported:** For *structural* facts (directory names, package names, file locations, which dirs contain tests, the internal/public boundary), a deterministic generator cannot lie. The output is a direct reflection of the filesystem and `go list` output. If the generator runs in CI and the output is checked with `git diff --exit-code`, drift is impossible without a failing build [8][9].

**Not supported:** For *semantic* content (reading paths, explanations of what each dir does, the "typical path" a new contributor follows), a generator can only produce a *draft*. The role of a directory is not encoded in the filesystem — it is a human decision. A generator can infer standard conventions (cmd/ = CLI entry point) but cannot know why a project chose a non-standard layout or what a custom directory actually does.

**The "generated pages can't lie" argument** is strongest for reference docs derived from a canonical source of truth (API specs, `--help` output, type definitions). For a structure.md, the "source of truth" is partly the filesystem (deterministic) and partly human intent (non-deterministic). The governance decision should therefore be: **generate the structural skeleton deterministically, require human review of semantic content, and use CI drift checks to prevent the generated skeleton from diverging.**

### The "hand-written can lie" risk

A hand-maintained structure.md can silently drift: directories are renamed, new ones added, test locations change, and no one updates the doc. The memstead project's approach is instructive: "The discipline isn't trust — it's a build error" [19]. Making drift a build error (via CI `git diff --exit-code`) is the key governance mechanism, regardless of whether the source is generated or hand-written.

## Findings Summary

### What is a REAL technical obstacle vs. a solvable detail

| Item | Assessment |
|------|-----------|
| Listing directories in a Go module | **Solved** — `go list ./...` is standard, deterministic, no deps |
| Inferring roles for standard dirs (cmd/, internal/, pkg/) | **Solved** — well-known conventions; a template can map dir name → role |
| Inferring roles for custom/non-standard dirs | **Real obstacle** — requires human annotation (e.g., `.structure.yml` or `// role:` comments) |
| Generating a one-line-per-dir markdown file | **Solved** — trivial template + `go list` output |
| Keeping generated file in sync via CI | **Solved** — `git diff --exit-code` pattern is proven [8][9] |
| Preventing hand-edits to generated file | **Solved** — `// Code generated ... DO NOT EDIT` convention [10] |
| Producing semantic reading-path explanations | **Real obstacle** — requires human judgment; generator can only draft |

### Objective conditions under which hand-written structure.md with validation-only freshness is acceptable

A hand-written structure.md with validation-only freshness checks is acceptable when:

1. The project has a **non-standard layout** where directory roles cannot be inferred from conventions alone, and the semantic content (reading paths, explanations) is the primary value.
2. The project already has a **strong review culture** where structure.md changes are reviewed alongside code changes (e.g., as part of a "new directory" PR checklist).
3. The validation check is **not just freshness** but **completeness** — e.g., a CI check that verifies every top-level directory has a corresponding entry in structure.md (a structural diff, not just a content diff).
4. The project is **small enough** (< 10 top-level dirs) that the maintenance burden is trivial.

### Recommended default policy: Generation-first with semantic exception

**Default**: Generate `structure.md` deterministically from `go list ./...` + a template that maps standard Go directory names to one-line roles. The generator runs via `//go:generate` and is checked in CI with `git diff --exit-code`. The generated file carries a `// Code generated ... DO NOT EDIT` marker.

**Exception**: For non-standard directories whose roles cannot be inferred from naming conventions, the generator emits a placeholder (e.g., `## custom-dir` with no role line). A human must fill in the role. The CI check still validates that the file exists and has an entry for every directory, but does not validate the semantic content of the role lines.

**This is the "generated skeleton + human semantic enrichment" pattern** — the same pattern used for CLI reference docs where `--help` output is generated but examples and `use:` one-liners are hand-written [19].

## Gaps

- No existing Go-specific tool was found that generates a per-directory role map out of the box. The closest tools (gomarkdoc, dirtree, projectscan) either focus on API docs or dependency graphs. A custom generator using `go list` + a template is the clear path.
- The agentskills.io spec and AGENTS.md ecosystem do not address structure.md generation specifically. The governance decision must be informed by the general "generated vs hand-maintained" pattern rather than a kit-specific precedent.
- The claim "generated docs cannot lie" is well-supported for structural content but not for semantic content. The brief recommends a hybrid approach; a pure-generation or pure-hand-written policy would both have gaps.
